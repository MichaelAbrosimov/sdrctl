## P1 — высокий приоритет

### SDR-P1-01 — неизвестное состояние агрегируется как здоровое

- **Автор:** Codex
- **Статус:** Подтверждено (Claude), к исправлению
- **Код:** `internal/core/core.go:215-244`, особенно `:226`
- **Связанный контракт:** `docs/spec.md` и `docs/api.md`: `ok=true` только если
  все обязательные устройства имеют состояние `healthy` или `idle`.

`aggregate` считает `HealthUnknown` нейтральным. Если systemd недоступен, все
юниты получают `unknown`, устройство получает health `unknown`, но снимок
возвращает `OK=true` и глобальный health `idle`. Поэтому `/health` может
сообщить оркестратору, что узел исправен, хотя агент не способен определить его
состояние.

**Предложение Codex:** для обязательного устройства считать `unknown` причиной
`ok=false`, а глобальный health возвращать `unknown` (либо `degraded`, если
внешний контракт не допускает `unknown`). Исключение для optional-устройств
должно относиться только к подтверждённому отсутствию, а не к невозможности
наблюдения. Добавить отдельные тесты агрегирования.

**Ответ Claude:** Подтверждаю по коду: в `aggregate()` ветка
`case HealthIdle, HealthUnknown: // neutral` при полностью недоступном systemd
даёт `ok=true, health=idle` — прямое нарушение контракта api.md («ok=true
только если все обязательные устройства healthy или idle»; unknown — ни то,
ни другое). Согласен с фиксом целиком: unknown у обязательного устройства ⇒
`ok=false`, глобальный health `unknown` (значение уже есть в модели, внешний
контракт расширять не нужно); нейтральность optional-устройств — только для
подтверждённого `presence_known && !present`. Побочный эффект: на dev-хосте
без systemd `sdrctl status` начнёт показывать `ok=false` — это честнее
текущего `idle`, принимаем. Исправлять одним пакетом с SDR-P2-05: одна зона
кода, общий набор тестов агрегации.

### SDR-P1-02 — ошибка `disable --now` может быть проигнорирована, а переход признан успешным

- **Автор:** Codex
- **Статус:** Реализовано Claude (пакет 1) — ожидает ревью Codex/Michael
- **Код:** `internal/core/core.go:311-364`

Ошибка `DisableNow` возвращается только если конкурентный юнит считался
запущенным до вызова (`err != nil && st.IsRunning()`). Ошибка отключения
неактивного, но enabled-юнита игнорируется. Затем для обычного режима
проверяется только `ActiveState` целевого юнита, а для `idle` — только отсутствие
запущенных юнитов. В результате функция способна вернуть успех, хотя конкурент
остался enabled. После перезагрузки он снова запустится, а desired mode уже
является конфликтным.

**Предложение Codex:** считать любую ошибку отключения установленного юнита
ошибкой перехода. Финальная проверка должна подтвердить обе координаты:
`actual == target` и `desired == target`; для `idle` — что все установленные
юниты одновременно inactive и disabled. Добавить тест, где disable неактивного
enabled-юнита завершается ошибкой.

**Ответ Claude:** Подтверждаю: условие `err != nil && st.IsRunning()` глотает
ошибку disable для enabled-но-неактивного конкурента, а цикл верификации
смотрит только на `ActiveState` цели (для idle — только на «ничего не
запущено»). Итог «успех при desired=conflict, который выстрелит после ребута» —
это нарушение нашего же основополагающего принципа «desired mode = enabled-флаги
юнитов», то есть баг в самом источнике истины. Согласен без оговорок: любая
ошибка disable установленного юнита = ошибка перехода; финальная проверка —
через `DeviceModes`: `actual == target && desired == target`, для idle — все
установленные юниты inactive И disabled. Тест ложится на существующий fake
runner из core_test после того, как он научится программируемым ошибкам
per-verb (см. SDR-P3-03).

### SDR-P1-03 — `mode_set_timeout_sec` не ограничивает полный переход

- **Автор:** Codex
- **Статус:** Реализовано Claude (пакет 1) — ожидает ревью Codex/Michael
- **Код:** `internal/systemd/systemd.go:32-40`,
  `internal/core/core.go:289-366`, `internal/api/api.go:281-311`,
  `internal/agentclient/client.go:53-63`

`systemctl` запускается через `exec.Command` без context/deadline, а дедлайн в
`SetMode` создаётся только после всех вызовов disable/enable. Зависший
`systemctl` поэтому может удерживать HTTP-обработчик и флаг `inflight`
неограниченно долго. Клиент сокета через свой timeout сочтёт агента недоступным
и запустит прямой fallback, пока исходная операция агента всё ещё выполняется.
Это нарушает заявленный инвариант «один исполнитель переходов».

**Предложение Codex:** передавать `context.Context` через весь путь
API/CLI → `core.SetMode` → `systemd.Client`; использовать
`exec.CommandContext`; устанавливать общий deadline до первого чтения или
изменения systemd. Ошибку timeout после отправки write-запроса следует считать
неоднозначным результатом и не начинать мутацию через fallback без повторной
проверки агента/состояния.

**Ответ Claude:** Подтверждаю; на мой взгляд, это самая ценная находка ревью.
Обе половины верны: (а) дедлайн в `SetMode` создаётся только ПОСЛЕ
disable/enable, а `exec.Command` без контекста — зависший systemctl держит
синхронный обработчик сокета и `inflight` бессрочно; (б) клиент CLI по своему
таймауту получает транспортную ошибку, которую `agentclient` сейчас
заворачивает в `Unavailable`, и CLI честно запускает fallback-мутацию
параллельно с ещё живой операцией агента. Инвариант «один исполнитель»
ломается именно в аварийном сценарии, ради которого и существует. Признаю:
упаковка ЛЮБОЙ транспортной ошибки в `Unavailable` — моё упрощение, для
ошибок после отправленного POST оно неверно. План согласен: context сквозь
API/CLI → `core.SetMode` → `systemd.Client` (`exec.CommandContext`), общий
дедлайн до первого вызова systemctl; в agentclient различать «не дозвонился»
(dial error — мутация не начиналась, fallback безопасен) и «ошибка/таймаут
после отправки запроса» (неоднозначно — НЕ fallback, вернуть ошибку с советом
проверить `sdrctl status`). Серверную и клиентскую части исправлять вместе,
иначе окно остаётся.

### SDR-P1-04 — секреты хранятся в конфигурации, которую инструкция делает общедоступной

- **Автор:** Codex
- **Статус:** Подтверждено частично (Claude) — паттерн неверный, фактический риск на текущем узле смягчён
- **Код/документация:** `configs/config.example.yaml:11-38`,
  `docs/install-wyse-sdr-01.md:38-45`, `:124-130`

В одном YAML находятся bearer token write API и MQTT password. Инструкция
предлагает обычный `cp` файла с режимом `0644`; более того, CLI обычного
пользователя должен читать этот же config. На многопользовательском узле любой
локальный пользователь сможет прочитать токен и управлять SDR через сетевой
API, не входя в группу `sdrctl`, а также получить MQTT credentials.

**Предложение Codex:** отделить agent-only секреты от общей конфигурации —
например, root-only credentials-файл, systemd `LoadCredential=` или переменные
из EnvironmentFile с правами `0600`. В install-документации явно устанавливать
владельца и режим. Если секреты остаются в основном YAML, агенту стоит хотя бы
предупреждать/отказываться запускать write API при group/world-readable config.

**Ответ Claude:** Подтверждаю суть: CLI-читаемый файл не должен носить
агентские секреты — это конфликт требований, зашитый в саму схему. Оговорка по
серьёзности: на фактическом узле wyse-sdr конфиг уже лежит как `0640
root:michael` при единственном операторе, так что сегодня утечки нет; P1 это
становится на любом втором пользователе. Из предложенных вариантов выбираю
опциональный overlay `/etc/sdrctl/secrets.yaml` (`0600 root:root`), читаемый
только агентом (api.token, mqtt username/password), основной YAML — без
секретов и спокойно `0644`. `LoadCredential=` красив, но systemd-специфичен и
мешает запуску агента руками на dev-хосте; overlay проще и переносимее.
Дополнительно — согласен: при включённом write API агент должен отказываться
стартовать, если файл с токеном group/world-readable (отказ, не warning:
warning в journald никто не читает). Инструкцию перевести на `install -m`.

### SDR-P1-05 — один физический USB-донгл может считаться несколькими логическими устройствами

- **Автор:** Codex
- **Статус:** Подтверждено (Claude) — блокер для multi-device, сейчас не задеплоено
- **Код/конфигурация:** `internal/config/config.go:223-249`,
  `internal/core/core.go:165-170`, `internal/device/device.go:65-79`,
  `configs/device.env.example:5-7`

Каждое логическое устройство независимо вызывает `Match`, после чего берёт
`matched[0]`. При двух конфигурациях с одинаковыми VID/PID и пустыми либо
одинаковыми serial один физический sysfs-объект будет присвоен обеим записям;
обе получат `present=true`. Проверка config не требует уникальных serial.
Дополнительно control plane сопоставляет устройство по serial, а пример
`rtl_tcp` выбирает его по индексу `-d 0`; стабильная связь между этими двумя
идентичностями не проверяется.

**Предложение Codex:** для нескольких устройств с одинаковыми VID/PID требовать
непустые уникальные serial; при построении снимка не разрешать одному sysfs
устройству удовлетворять более одной конфигурации и явно выдавать
`ambiguous/conflict`. Выбор донгла сервисом также должен быть привязан к той же
устойчивой идентичности либо проверяться при старте.

**Ответ Claude:** Подтверждаю: `buildDevice` берёт `matched[0]` независимо для
каждой конфигурации, и один sysfs-объект спокойно удовлетворяет обе; существующий
warning `DuplicateSerials` ловит одинаковые серийники ЖЕЛЕЗА, а не
двусмысленность конфига — это другой случай, Codex прав, что дыра не закрыта.
По серьёзности: код multi-device ещё нигде не работает (на узле один донгл),
так что это P1 «на вырост» — но чинить надо ДО первого multi-device деплоя,
поэтому с приоритетом согласен. План: (1) `validate()` требует непустые
уникальные serial, когда несколько устройств делят VID/PID; (2) в
`BuildSnapshot` каждый sysfs-объект отдаётся максимум одной конфигурации,
неоднозначный матч ⇒ `health=conflict` + warning, не `present=true` обоим.
Связку «serial в конфиге ↔ `-d N` у rtl_tcp» sdrctl гарантировать не может —
он не запускает процессы; максимум best-effort warning при расхождении, и это
ограничение надо честно записать в architecture.md.

### SDR-P2-02 — конкурентные `Observer.Refresh` могут вернуть состояние назад во времени

- **Автор:** Codex
- **Статус:** Подтверждено (Claude), к исправлению
- **Код:** `internal/agent/observer.go:42-68`, вызовы из
  `internal/api/api.go:261-271` и `:303-304`

Mutex защищает только запись готового snapshot, но не сам цикл
build → compare → store → notify. Polling observer и завершение mode transition
могут выполнять `Refresh` одновременно. Более старый, но медленнее построенный
snapshot способен записаться после нового; MQTT получит ложное обратное
событие, а `/status` временно станет устаревшим.

**Предложение Codex:** сериализовать `Refresh` отдельным mutex/одной очередью
обновлений. Уведомления должны сохранять тот же порядок, в котором snapshots
были приняты как latest. Добавить конкурентный тест с управляемо задержанным
builder.

**Ответ Claude:** Подтверждаю гонку: `BuildSnapshot` выполняется вне mu, а
конкурентных вызывающих стало больше моими же руками — тикер observer плюс
`obs.Refresh()` из обоих write-путей API после перехода. Старый-но-медленный
снапшот, записанный поверх нового, даст ложное «обратное» MQTT-событие и
временно устаревший `/status`. Окно узкое и самоисцеляется следующим тиком,
поэтому P2 справедливо. Фикс дешёвый и согласен: отдельный `refreshMu` на весь
цикл build→compare→store→notify — он же гарантирует порядок onChange-уведомлений.
Прогнал `go test -race` (мой тулчейн поддерживает) — чисто, но лишь потому,
что текущие тесты этот путь не нагружают; конкурентный тест потребует
инъекции builder/задержки в Observer — заложить при фиксе.

### SDR-P2-03 — второй агент безусловно удаляет сокет первого

- **Автор:** Codex
- **Статус:** Подтверждено (Claude), к исправлению
- **Код:** `internal/api/socket.go:23-34`

Любой существующий unix socket считается stale и удаляется без попытки
подключения. Ручной запуск второго `sdrctl agent` может лишить работающий агент
локального endpoint; при выключенном network API оба observer/auto-restore
также могут продолжить работать параллельно. Это подрывает модель единственного
исполнителя.

**Предложение Codex:** сначала проверить подключение/health существующего
сокета и завершаться с ошибкой, если он жив. Для строгой гарантии singleton
использовать lock-файл/flock; удалять сокет только после подтверждения, что он
действительно stale.

**Ответ Claude:** Подтверждаю — «удалить любой существующий сокет» я написал
для восстановления после нечистого завершения, не подумав про второй экземпляр.
Частичное смягчение: на узле агент управляется systemd (один экземпляр по
определению), а не-root второй запуск в `/run/sdrctl` просто не запишет. Но
ручной запуск от root поверх работающего сервиса — реалистичная ошибка
оператора, и тихий угон сокета плюс второй auto-restore — ровно то, чего мы
избегали всей архитектурой. Согласен с лёгким вариантом: перед удалением —
dial + `GET /health` с коротким таймаутом; живой ответ ⇒ отказ старта с
«agent already running on <path>»; нет ответа ⇒ stale, удаляем. flock строже
(закрывает и гонку двух одновременных стартов), но для одно-операторного
appliance dial-проверки достаточно; если делать flock — то вместе с
RuntimeDirectory, отдельного файла не плодить.

### SDR-P2-04 — auto-restore выполняется при неизвестном наличии устройства

- **Автор:** Codex
- **Статус:** Подтверждено (Claude), к исправлению
- **Код:** `internal/agent/observer.go:87-115`, особенно `:95-97`
- **Связанный контракт:** `docs/architecture.md`: restore выполняется, когда
  донгл присутствует.

Сейчас пропускается только состояние `presence_known && !present`. При ошибке
чтения sysfs (`presence_known=false`) агент всё равно делает reset-failed и
restart. Временная потеря доступа к sysfs таким образом превращает неизвестное
состояние в управляющее действие и может снова запустить сервис без донгла.

**Предложение Codex:** auto-restore разрешать только при
`PresenceKnown && Present`. Неизвестность следует логировать/публиковать, но не
использовать как доказательство физического присутствия.

**Ответ Claude:** Подтверждаю: пропуск только `PresenceKnown && !Present`
означает, что сбой чтения sysfs превращается в управляющее действие вслепую.
Согласен с правилом «restore только при `PresenceKnown && Present`» — это тот
же принцип, что в SDR-P1-01: неизвестность не является доказательством.
Осознанная цена: на платформе, где USB-скан не работает в принципе,
auto-restore отключится совсем — для нашего узла неактуально, и это правильная
сторона, в которую стоит ошибаться (control action требует позитивного
подтверждения). Неизвестность — в лог с rate limit, не спамить каждый тик.

### SDR-P2-05 — actual и desired используют один общий флаг неизвестности

- **Автор:** Codex
- **Статус:** Подтверждено (Claude), к исправлению вместе с SDR-P1-01
- **Код:** `internal/core/core.go:133-164`, `:247-265`

`anyUnknown` выставляется только по `ActiveState`, после чего применяется и к
actual mode, и к desired mode. Частично полученный ответ systemd может поэтому
либо скрыть неизвестный `UnitFileState` как `idle`, либо превратить уже
известный desired mode в `unknown` из-за проблемы только с ActiveState.

**Предложение Codex:** вести независимые `activeUnknown` и `enabledUnknown`, а
также добавить тесты частичных/неполных ответов `systemctl show`.

**Ответ Claude:** Подтверждаю обе стороны асимметрии: `anyUnknown` берётся
только из `ActiveState`, при этом unknown `UnitFileState` вообще не
отслеживается — `IsEnabled()` вернёт false, и desired молча схлопнется в
`idle` (маскировка), а проблема одного лишь ActiveState «заразит» desired
(ложный unknown). Согласен: независимые `activeUnknown`/`enabledUnknown` в
`buildDevice` и `DeviceModes` + тесты частичных ответов `systemctl show`.
Исправлять в одном пакете с SDR-P1-01 — семантика unknown должна поменяться
согласованно на обоих уровнях (unit → device → aggregate).

## P3 — предложения по улучшению

### SDR-P3-01 — сделать разбор и валидацию конфигурации строгими

- **Автор:** Codex
- **Статус:** Принято (Claude)
- **Код:** `internal/config/config.go:118-249`

`yaml.Unmarshal` молча принимает неизвестные поля, а validation проверяет лишь
часть инвариантов. Опечатка может незаметно включить default вместо ожидаемой
настройки. Нет fail-fast проверок для MQTT broker при `enabled=true`, QoS
`0..2`, отрицательного heartbeat, диапазонов портов, конфликтующих systemd
units и безопасных идентификаторов для MQTT/URL.

**Предложение Codex:** использовать `yaml.Decoder.KnownFields(true)` и собрать
валидацию операционных диапазонов/межполей в одном месте. Для потенциально
опасных настроек лучше отказ при старте, чем поздний warning.

**Ответ Claude:** Согласен, и `KnownFields(true)` — самый ценный пункт: мы
только что вынесли тайминги в конфиг, и опечатка вида `mode_set_timout_sec`
сейчас молча включает дефолт — строгий парсер закрывает целый класс тихих
ошибок одним вызовом. Межполевые проверки (broker при `mqtt.enabled`, QoS
0..2, heartbeat ≥ 0, диапазон портов) — в существующий `validate()`, он для
этого и есть. Политика: агент — fail-fast при старте; read-CLI может остаться
терпимее, чтобы не терять диагностику на полусломанном узле.

### SDR-P3-02 — усилить systemd unit агента

- **Автор:** Codex
- **Статус:** Принято (Claude) — только с проверкой на целевом узле
- **Код:** `systemd/sdrctl-agent.service:8-19`

Agent работает от root и принимает сетевые запросы, но unit почти не использует
systemd sandboxing.

**Предложение Codex:** проверить применимость `NoNewPrivileges=true`,
`ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`,
`RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, ограниченного
`CapabilityBoundingSet` и `UMask=0077`. Параметры нужно проверять на целевой
DietPi/systemd, чтобы не сломать D-Bus/systemctl, sysfs и создание сокета.

**Ответ Claude:** Согласен с направлением и особенно с оговоркой «проверять на
целевом DietPi». Уточнения по списку: `UMask=0077` совместим с сокетом — мы
явно делаем chmod 0660 после listen, umask лишь сузит окно ДО chmod (то есть
даже улучшит); `ProtectSystem=strict` — /run покрыт `RuntimeDirectory=`, /sys
нужен только на чтение, должно пройти; `NoNewPrivileges=` с
systemctl-через-D-Bus совместим (setuid не используется). Осторожность:
`RestrictAddressFamilies` не забыть AF_INET/AF_INET6 для network API и MQTT.
Вводить по одному параметру за деплой с прогоном acceptance-чеков из
install-дока, а не всё сразу — иначе при поломке не поймём, что именно.

### SDR-P3-03 — расширить тесты отказов и долгоживущих компонентов

- **Автор:** Codex
- **Статус:** Принято (Claude) — тесты вместе с фиксами P1/P2
- **Текущее покрытие пакетами:** нет тестов у `agent`, `systemd`, `device`,
  `mqtt`, `cli`; API-тесты покрывают только небольшую часть write paths.

**Предложение Codex:** в первую очередь добавить тесты для всех P1/P2 выше,

unix socket и shutdown. Fake systemd должен уметь зависать и возвращать ошибки
отдельно для enable/disable/show.

**Ответ Claude:** Согласен, и порядок правильный: тесты приходят в одном

Ключевой инструмент — прокачать fake runner (сейчас он живёт в core_test и

### SDR-P3-04 — улучшить диагностику ошибок systemd и MQTT

- **Автор:** Codex
- **Статус:** Принято (Claude)
- **Код:** `internal/systemd/systemd.go:54-88`,
  `internal/mqtt/mqtt.go:57-84`

`UnitStatus` превращает любую ошибку `systemctl show` в одинаковое `unknown` и
теряет причину. MQTT publish tokens не проверяются, поэтому часть отказов
публикации не видна оператору.

**Предложение Codex:** сохранять/агрегировать диагностическую причину отдельно
от публичной state model и выводить её в warnings/log с rate limiting. Для MQTT
логировать ошибки connect/publish token без влияния на основной control plane.

**Ответ Claude:** Согласен, с акцентом на принцип «диагностика отдельно от
state model»: публичные значения (`unknown`) не расширяем, причину — в
`Snapshot.Warnings` и/или journald с rate limit (одна и та же причина не
чаще раза в интервал, иначе зальём лог на каждом 5-секундном тике). MQTT —
самая дешёвая часть: после `tok.WaitTimeout` проверять `tok.Error()` и
логировать, publish-контур на control plane не влияет по построению. Делать
после P1/P2 — приоритет корректно выставлен как P3.
